- 当前掌握程度为“部分掌握”。第 3、5 点方向正确；第 1、4 点需要修正；第 2、6 点需要补全。
- 第 1 题的完整过程是：浏览器先通过 `JSON.stringify()` 把 JavaScript 对象变成 JSON 字符串，再编码为 UTF-8 字节并通过 HTTP 发送；Node.js 从 request 可读流中获得 Buffer，合并后进行 UTF-8 解码，最后用 `JSON.parse()` 恢复为 JavaScript 数据。
- 第 2 题：网络传输的是字节而不是 JavaScript 对象；Node.js 原生 HTTP 层也不能假定所有请求都是 JSON，所以它只提供通用的 `IncomingMessage` 可读流。读取、大小限制、字符解码和 JSON 解析需要应用代码或框架中间件完成。

- 第 5 题方向正确。`Content-Type: application/json` 只是声明数据的媒体类型，便于接收方选择解析方式；它不会自动调用 `JSON.parse()`。原生 Node.js 中仍需手动解析，Express 等框架则可能通过中间件代劳。

- 当前掌握程度为“基本掌握”。第 1、3、5、6 点方向正确，第 2、4 点需要补充更准确的技术原因。
- 第 1 题：SSE 会保持一条 HTTP 响应连接，并按事件持续发送数据；一次性 JSON 要等完整响应体接收完成后才能整体解析。更准确的说法是“分段或增量获取”，而不是“分流”。流式输出通常只是更早显示首段内容，不代表模型完成整次生成的总时间一定更短。

- 建议复述重点：`网络 chunk 是传输分片，SSE event 是协议事件，delta 是业务文本增量，TextDecoder 负责跨 chunk 正确还原字符。`

1. TypeScript 只在开发和编译阶段检查代码类型，编译成 JavaScript 后类型会被擦除。网络返回的数据来自程序外部，可能缺少字段、字段类型错误、结构变化或包含恶意内容，因此 TypeScript 声明不能证明运行时数据符合类型，必须额外进行运行时校验。

5. 流式内容已经显示一部分后发生错误，当前程序如何处理历史和日志？

我的结论：

> 待补充

参考答案：

1. `async/await` 用于等待不会立即完成的异步操作，同时保持代码接近同步流程的可读性。模型请求中，`callModel()` 等待 `fetch`、错误正文和完整 JSON，`streamModel()` 还通过 `for await...of` 持续等待 SSE 数据；HTTP 请求体处理中，`readJsonBody()` 通过 `for await...of request` 逐块读取 body，收完后才合并和解析；日志处理中，程序等待目录创建与 JSONL 追加写入完成，并在写入失败时进入错误处理。`await` 会暂停当前 async 函数的后续步骤，但不会阻塞整个 Node.js 事件循环。
2. 每次模型请求都会创建 `AbortController`，并把 `controller.signal` 传给 `fetch`。`setTimeout()` 到达 `MODEL_TIMEOUT_MS` 后调用 `controller.abort()`，中止仍未完成的请求；捕获到名为 `AbortError` 的错误后，代码把它转换成更明确的 `ModelApiError`。无论成功还是失败，`finally` 都要执行 `clearTimeout(timeout)`，避免已完成请求的定时器之后再次触发，并及时释放定时器相关资源。
3. 网络错误表示请求未能正常连接或传输，例如 DNS、拒绝连接或断网，当前代码统一转换为“无法连接模型服务”；超时表示请求在允许时间内没有完成，是应用通过 AbortController 主动中止的结果；非 2xx HTTP 响应表示已经联系到上游服务，但它明确返回失败状态，例如 400、401、429 或 500，代码会保留 HTTP 状态用于服务端诊断；响应格式错误表示 HTTP 请求可能成功，但返回的 JSON 或 SSE 结构不符合 Zod Schema，程序不能安全读取其中字段。四者发生的层次和处理、重试策略并不相同。
4. 客户端错误说明浏览器提交的数据不符合接口要求，应返回 `400`、`413` 或 `415`，通常不应调用模型；模型上游错误说明自己的 HTTP 服务可用，但模型调用失败，应向浏览器返回通用 `502`，并在服务端记录具体原因；未知内部错误可能是代码缺陷、文件读取失败或未预料异常，应返回通用 `500`。分类处理能提供正确 HTTP 语义、帮助客户端决定是否修正或重试，也能避免把堆栈、上游正文和敏感实现细节泄露给浏览器。
5. `streamModel()` 每收到 `delta.content` 就通过回调写到终端，所以中途失败前的部分文字已经可见，无法撤回。但它只有在流完整结束并得到有效完整回答后才 resolve；CLI 只在 `await streamModel()` 成功后调用 `session.commitTurn()` 和追加 JSONL 日志。因此流中途失败时，已显示的部分内容不会进入正式对话历史，也不会作为成功记录写入日志，下一轮请求不会把这段不完整回答发送给模型。

## 11. 确定性代码与模型职责

1. 哪些行为必须由确定性代码负责，例如校验、权限、超时和历史窗口？
2. 哪些行为适合交给模型，例如自然语言理解和回答生成？
3. 为什么不能把安全判断完全交给 system prompt？
4. 如果模型输出格式错误，应该由模型“自觉修复”，还是由代码检测并决定重试或失败？

我的结论：

> 待补充

参考答案：

1. 只要行为要求结果稳定、可验证、涉及安全或可能产生真实副作用，就应该由确定性代码负责。当前项目中包括：读取和校验环境变量；保护 API Key；验证 Content-Type、请求体大小和 `question`；构造并锁定 system 消息；检查 HTTP 状态和模型响应 Schema；设置超时并中止请求；限制最大输出 token 和历史轮数；只在模型完整成功后提交历史；映射 400、413、415、500、502 等错误；写入日志并避免记录凭证。未来的身份认证、用户权限、数据库归属检查、工具白名单、金额限制、高风险确认、最大 Agent 步数、幂等和重试次数也必须由代码控制，不能让模型自行决定是否执行。
2. 模型适合处理边界模糊、依赖语义理解、无法用少量固定规则穷举的问题，例如理解自然语言意图、总结文章、提取关键信息、改写文本、生成回答、对内容分类、根据候选工具描述建议使用哪个工具，以及在提供的上下文中组织解释。即使模型负责这些任务，它的输入范围、可用工具、输出 Schema、调用次数和最终副作用仍应由代码限制和验证。
3. system prompt 只是发送给概率模型的一段高优先级指令，它能提高模型遵循规则的概率，但不是身份认证、授权系统或安全沙箱。用户仍可能在 question、网页、文档或工具返回值中放入提示词注入；模型也可能误解、忽略或错误执行规则。如果把安全判断完全交给 system prompt，模型一旦判断错误就可能泄露数据或执行越权操作。真正的安全边界必须由模型之外的确定性代码实现，例如根据登录状态查询数据、检查资源是否属于当前用户、限制工具和参数，并在人为确认后才执行高风险操作。
4. 不能等待模型“自觉发现”格式错误。模型输出首先应被当作 `unknown`，由代码执行 `JSON.parse()` 和 Zod `safeParse()`；校验成功后才能进入业务逻辑。校验失败时，代码可以根据任务风险决定：携带简化后的校验错误要求模型重新生成，并设置明确的最大重试次数；使用安全的降级结果；或者直接返回结构化错误。模型可以参与修复内容，但“是否错误、是否重试、最多重试几次、修复后是否合格、失败后是否停止”都必须由代码决定。不能无限重试，也不能用 `as` 强行把错误输出当成正确类型。

职责判断原则：

```text
确定性代码：校验、权限、限制、状态、重试策略、真实副作用和最终裁决
模型：理解、生成、总结、分类、提取和提出候选决策
```

一个可靠的 Agent 不是让模型控制一切，而是让模型在代码划定的边界内处理不确定性。
