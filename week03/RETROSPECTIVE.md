### 第 1 节检查与补充

整体评价：已经理解代码需要负责校验和异常处理，但工具清单、工作流的含义、命令运行方式，以及模型与工具的职责边界还需要修正。

1. 工具清单：本周注册的是计算器 `calculator`、时间查询 `get_current_time`、本地知识查询 `search_knowledge`，不是“调模型工具”。计算器在本地 Node.js 中根据参数计算；时间工具读取运行机器的时钟并转换时区；知识工具在 Node.js 中通过 fetch 请求本地知识 HTTP 服务，查询 `src/knowledge.ts` 的固定教学条目。`modelCaller` 是请求模型的接口，不是本项目向模型注册的工具。

2. 适用场景：直接请求模型适合无需外部操作的总结、改写、解释等任务，不是仅按任务是否简单或一次性区分。固定工作流是由代码预先规定步骤，例如“读取文章 → 请求摘要 → 校验 → 保存”；它不等于使用 skill。Agent 循环的关键是根据中间结果动态决定下一步，例如查询资料后发现信息不足，再调整查询。简单算术不必为此引入 Agent；若要求计算结果可靠，也可以直接执行计算代码，无需让模型参与。

3. 命令职责：`pnpm start` 运行 `src/index.ts`，由命令行参数选择工具并执行，不请求模型；不带参数时默认计算 12 + 8。`pnpm agent` 运行真实模型模式，需要提供问题和模型配置，完成单次任务后退出，并不是启动常驻 HTTP 服务。`pnpm agent:demo` 运行固定的模拟模型流程，真实执行本地计算器，但不请求模型 API，完成后同样退出。`pnpm serve` 才是启动持续监听的本地知识 HTTP 服务。

4. 职责边界：不能笼统地说“具体问题的执行结果由模型负责”。真实模式下，模型提出是否调用工具、工具名称和参数，并根据反馈继续决策、组织最终回答；程序负责白名单、参数校验、执行工具、错误反馈、超时、预算和重复检测。实际计算结果由计算器生成，时间来自机器时钟，知识查询结果来自本地服务，不是模型生成。demo 中的决策则由模拟函数写死。

### 第 2 节检查与补充

整体评价：第 1、2 点方向正确，第 3、4 点需要补充原因；第 5 点需要修正，不能把错误类别直接等同于“结束、自动修复、自动重试”三种固定处理方式。

1. 定义、注册与执行：`defineTool()` 不仅定义工具，还把“先校验原始参数，再调用 execute”封装为统一的 `invoke()`。定义时不会立即执行业务函数。`ToolRegistry` 用 Map 按名称保存工具，拒绝重名注册，并提供查找和列表功能；这里不是直接把工具加入发送给模型的 tools 数组，后者由 `buildTools()` 转换生成。`executeTool()` 根据名称查找工具、调用 invoke、记录耗时和输入输出，并区分参数校验错误与内部执行错误。

2. 工具组成：你的理解正确。名称用于注册和查找，描述帮助模型理解用途，输入 Schema 规定参数结构与约束，执行函数完成实际计算或查询。Schema 既用于本地运行时校验，也可转换为模型可读的参数说明；执行函数本身不会发送给模型。

3. 注册表的意义：不只是“执行确定的工具”，更是白名单边界。模型返回的名称属于不可信输入，可能不存在或不被允许；只能查找开发者明确注册的工具，不能把名称当成代码执行，也不能允许模型任意访问本地函数。注册表控制可用工具范围，但不等于已经实现用户级权限校验。

4. TypeScript 与运行时校验：你已理解两者发生在不同阶段。关键不只是 Zod “更精细”，而是 TypeScript 类型在运行时不提供输入验证，无法保证模型或网络返回的数据符合声明。JSON.parse 检查 JSON 语法并将文本转成 JavaScript 值；Zod 再检查这个值是否符合参数结构和业务约束。例如除数 0 是合法 JSON、也是 number，但可以被 Zod 的除零规则拒绝。

5. 三类工具错误与后续处理：

   - 未知工具：registry 中找不到名称，执行器抛出 ToolNotFoundError；在 runAgent 中被转换为 unknown-tool，并作为工具结果返回模型，不会仅因这一错误立即结束整个任务。模型可以重新选择已注册工具。
   - 参数不合法：工具已找到，但输入未通过 Zod 校验，业务 execute 不会运行；runAgent 返回 invalid-arguments。程序不会直接改写参数，真实模式由模型决定是否修正，且不保证修复成功；demo 的修正逻辑才是写死的。
   - 工具内部执行失败：参数通过后，实际执行发生异常，例如网络连接失败。执行器包装为 ToolExecutionError；runAgent 保留知识请求的错误分类，其他情况返回 execution-error。当前没有在执行器中自动重试，模型收到反馈后可以提出新的调用，也可以解释失败；再次调用仍受预算和重复检测限制，并非所有错误都适合重试。

   还要区分入口：直接使用 pnpm start 时没有 Agent 循环，工具失败会打印错误并退出；上述“反馈给模型后继续决策”指的是 runAgent 流程。模型 API 自身失败则是另一条路径，当前会以 model-error 停止。

建议巩固：错误分类描述“哪里出了问题”，恢复策略描述“接下来怎么办”，二者不能简单一一对应。
